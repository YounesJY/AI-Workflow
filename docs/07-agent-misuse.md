# Agent Misuse



## 1. Prompt Mistakes

### 1.1 Why shouldn't the agent write my prompts?

The source says agents add unnecessary detail to descriptions. That is a fair warning: an agent-generated prompt often restates the task, adds generic quality language, and buries the actual constraint.

Write the prompt yourself when the task matters. Use the agent to critique the prompt, not to invent it.

> ⚠️ Verify: This is the source's opinion, not a measured rule. An agent can help draft a prompt when you review and cut it afterward.

### 1.2 Why are ambiguous, detail-less, and general prompts a problem?

Bad prompts force the model to guess. Guessing burns tokens and produces work you did not ask for.

| Bad                  | Better                                                                                                                                               |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| "Fix the bug"        | "The login form returns 401 after a correct password. Here is the stack trace and the auth middleware. Find the cause; do not change the API shape." |
| "Make the UI better" | "The settings page overflows on mobile at 375px. Fix the layout and attach a screenshot after the change."                                           |
| "Build the backend"  | "Add a POST /users endpoint with validation and tests. Follow the existing handler pattern in `src/api/`."                                           |

### 1.3 How do I provide the evidence?

- **Paste the error.** Full stack trace, not a summary.
- **Attach the screenshot.** UI bugs are hard to describe and easy to show.
- **Name the files.** Point at the relevant module instead of making the agent search the whole tree.
- **State the constraint.** "Do not change the API", "keep the existing schema", "no new dependencies."

The source's point is simple: the agent cannot reason about intent it was never given.

## 2. Context-File Mistakes

### 2.1 Why is a bad AGENTS.md worse than none?

The source says "not having one is better than having a bad one." That is correct. A stale or contradictory guidance file loads on every request and actively misleads the agent.

- **Remove stale instructions.** Old commands and renamed folders cause wrong actions.
- **Remove contradictions.** Two rules that disagree let the agent pick either one.
- **Keep it short.** The official Claude Code guidance is under 200 lines per file; the source recommends around 100 lines.

### 2.2 Why not ship an unreviewed generated file?

The source says a reviewed 20-line file beats an unreviewed 150-line file generated by AI. The reason is context cost and trust: every line is loaded, and an unreviewed line can be wrong.

Generate a draft with `/init` if you want, then edit it yourself. Remove anything you cannot verify.

### 2.3 What belongs in the file?

- Build, test, and run commands.
- Architecture and where to find things.
- Conventions that are not obvious from the code.
- Hard rules: files not to touch, APIs not to change, secrets handling.
- Project status and major changes, under `## IMPORTANT NOTES`.

Do not paste the whole README or a long design document. Link or reference it instead.

## 3. Session Mistakes

### 3.1 Why one long feature per session?

Context rot is the reason. The longer the session, the more the model loses middle details and follows stale decisions.

The source recommends "FeaturePerSession": finish one feature, commit, start a new session. If you must continue, compact or write a handoff first.

### 3.2 Is compaction a free reset?

Compaction summarizes the old conversation; it does not restore a clean context. It is better than running until the window is full, but a handoff file plus a new session is cleaner.

### 3.3 Why not mix unrelated work?

Debugging a deploy, designing a UI, and writing docs in one session crowds the context with unrelated details. Split by task.

## 4. Task-Sizing Mistakes

### 4.1 Why not ask for the whole platform at once?

"Build me a platform that does X, Y, and Z" produces a broad, shallow result. The agent spreads attention across too many concerns, and errors are hard to isolate.

Break the work into small features:

1. Define the data model.
2. Add one endpoint with tests.
3. Add the UI for that endpoint.
4. Repeat.

Each step has a clear success condition, which makes review and error catching easier.

### 4.2 How do I keep the scope reviewable?

If you cannot review the diff in one sitting, the task is too large. Split it before the agent starts, not after it produces 2,000 lines.

## 5. Delegation Mistakes

### 5.1 Why not make the primary agent do everything?

The primary agent's context is the scarce resource. If it reads every file, tries every failed approach, and writes every line, its context fills before the work is done.

The source recommends spawning subagents and delegating the work. That keeps the main context clean. The tradeoff is token cost: each subagent makes its own model calls.

### 5.2 What work should I delegate?

| Delegate                         | Keep in the primary                   |
| -------------------------------- | ------------------------------------- |
| Codebase exploration             | Final decisions                       |
| Research and docs lookup         | User-facing requirements              |
| Independent review               | Merge and conflict resolution         |
| Parallel, non-overlapping slices | Work that needs the full conversation |

### 5.3 How should I review the result?

A subagent returning a summary is not proof that the work is correct. Inspect the diff, run the tests, and check the files it touched.

## 6. Pre-Flight Checklist

| Check          | Question                                                    |
| -------------- | ----------------------------------------------------------- |
| **Prompt**     | Is the task specific, with files, errors, and constraints?  |
| **Scope**      | Can I review the diff in one sitting?                       |
| **Context**    | Is this a fresh session, or is the context already crowded? |
| **Guidance**   | Is `AGENTS.md` / `CLAUDE.md` current and short?             |
| **Evidence**   | Did I attach the error, screenshot, or reference?           |
| **Delegation** | Should a subagent do the research or review?                |
| **Recovery**   | Is the work committed, so I can revert if needed?           |

---

## 📌 Summary

| Mistake                              | Fix                                                       |
| ------------------------------------ | --------------------------------------------------------- |
| Letting the agent write the prompt   | Write it yourself; ask the agent to critique it           |
| Vague or general prompts             | Name the files, error, expected behavior, and constraints |
| Missing evidence                     | Paste stack traces; attach screenshots; link references   |
| Unreviewed `AGENTS.md` / `CLAUDE.md` | Keep it short, current, and manually verified             |
| Many features in one session         | One feature per session; commit and start fresh           |
| One huge task                        | Split into small, reviewable features                     |
| Primary agent doing everything       | Delegate research and review to subagents                 |
| Assuming the summary is correct      | Inspect the diff and run the tests                        |
